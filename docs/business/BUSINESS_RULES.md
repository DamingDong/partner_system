# 业务规则文档 (BUSINESS_RULES) - 合作伙伴管理系统

## 📋 文档概述

### 文档目的
本文档定义了合作伙伴管理系统的核心业务规则，确保系统行为的一致性和可预测性。所有技术实现必须严格遵循本文档定义的规则。

### 适用范围
- 系统开发团队：技术实现的依据
- 产品团队：功能设计的基准
- 业务团队：业务逻辑的参考
- 测试团队：测试用例的验证标准

### 规则分类
- **核心业务规则**：系统必须遵守的基本规则
- **数据验证规则**：数据完整性和准确性规则
- **业务流程规则**：业务流程流转规则
- **权限控制规则**：用户权限和访问控制规则

## 🔄 核心业务规则

### 1. 订单类型与分账规则

#### 1.1 订单类型定义
```typescript
// 订单类型枚举
type OrderType = 'ACTIVATION' | 'SUBSCRIPTION';

// 订单类型业务规则
const ORDER_TYPE_RULES = {
  ACTIVATION: {
    description: '激活订单 - 用户激活会员卡产生的订单',
    triggers: ['会员卡激活成功'],
    revenueSharing: false,  // 不参与分账
    purpose: '记录激活行为，不产生分账收益'
  },
  SUBSCRIPTION: {
    description: '订阅订单 - 用户续费或升级服务产生的订单',
    triggers: ['服务续费', '服务升级'],
    revenueSharing: true,   // 参与分账
    purpose: '产生分账收益，按照分账规则计算佣金'
  }
};
```

#### 1.2 分账适用性规则
**规则 BR-001**: 分账规则仅适用于订阅订单
- **规则描述**: 只有订单类型为 SUBSCRIPTION 的订单才参与分账计算
- **适用场景**: 所有分账计算和佣金分配
- **例外情况**: 无
- **验证逻辑**: 
  ```typescript
  function isEligibleForRevenueSharing(orderType: OrderType): boolean {
    return orderType === 'SUBSCRIPTION';
  }
  ```

### 2. 会员卡生命周期规则

#### 2.1 会员卡状态流转规则
**规则 BR-002**: 会员卡状态必须按预定顺序流转
```typescript
// 状态流转规则
const CARD_STATUS_TRANSITIONS = {
  PENDING_BIND: ['BOUND', 'CANCELLED'],      // 待绑定 → 已绑定/已销卡
  BOUND: ['ACTIVE', 'CANCELLED'],           // 已绑定 → 已激活/已销卡
  ACTIVE: ['EXPIRED', 'CANCELLED'],         // 已激活 → 已过期/已销卡
  EXPIRED: ['CANCELLED'],                   // 已过期 → 已销卡
  CANCELLED: []                             // 已销卡 → 终态
};

// 状态流转验证
function isValidStatusTransition(from: CardStatus, to: CardStatus): boolean {
  const allowedTransitions = CARD_STATUS_TRANSITIONS[from];
  return allowedTransitions ? allowedTransitions.includes(to) : false;
}
```

#### 2.2 会员卡绑定规则
**规则 BR-003**: MAC地址绑定具有最高优先级
- **规则描述**: 当会员卡需要绑定时，MAC地址绑定优先于其他绑定方式
- **绑定优先级**: 
  1. MAC地址绑定（设备唯一性）
  2. 渠道包绑定（业务渠道）
  3. 用户绑定（个人账户）

**规则 BR-004**: 绑定信息必须唯一
- **规则描述**: 同一MAC地址、渠道包或用户只能绑定一张有效会员卡
- **验证逻辑**: 
  ```typescript
  async function validateBindingUniqueness(bindingInfo: BindingInfo): Promise<boolean> {
    const existingCard = await findCardByBindingInfo(bindingInfo);
    return !existingCard || existingCard.status === 'CANCELLED';
  }
  ```

### 3. 分账计算规则

#### 3.1 分账规则优先级
**规则 BR-005**: 条件式分账规则优先级最高
```typescript
// 分账规则优先级定义
const REVENUE_RULE_PRIORITY = {
  CONDITIONAL: 100,    // 条件式分账（最高优先级）
  TIERED: 80,         // 阶梯式分账
  FIXED: 50,          // 固定比例分账
  DEFAULT: 0          // 默认规则（最低优先级）
};

// 规则匹配逻辑
function matchRevenueRule(transaction: Transaction): RevenueRule {
  const applicableRules = getApplicableRules(transaction);
  return applicableRules.sort((a, b) => 
    REVENUE_RULE_PRIORITY[b.type] - REVENUE_RULE_PRIORITY[a.type]
  )[0];
}
```

#### 3.2 分账金额计算规则
**规则 BR-006**: 分账金额必须精确到分
- **规则描述**: 所有金额计算必须保留两位小数，采用银行家舍入法
- **计算精度**: 0.01元（1分）
- **舍入规则**: 四舍六入五成双

**规则 BR-007**: 分账比例必须在有效范围内
- **规则描述**: 分账比例必须在0%到100%之间（包含边界）
- **有效范围**: [0, 100]
- **验证逻辑**: 
  ```typescript
  function validateCommissionRate(rate: number): boolean {
    return rate >= 0 && rate <= 100;
  }
  ```

### 4. 对账业务规则

#### 4.1 对账周期规则
**规则 BR-008**: 对账周期必须完整覆盖
- **规则描述**: 对账周期必须从周期开始日的00:00:00到结束日的23:59:59
- **时间精度**: 精确到秒
- **周期完整性**: 不允许部分周期对账

#### 4.2 对账数据一致性规则
**规则 BR-009**: 对账数据必须与原始交易数据一致
- **规则描述**: 对账单中的交易数据必须与原始交易记录完全匹配
- **一致性检查**: 金额、时间、状态等关键字段必须一致
- **差异处理**: 发现差异必须暂停对账并人工介入

## 📊 数据验证规则

### 5. 数据格式规则

#### 5.1 会员卡数据验证
**规则 DV-001**: 会员卡号必须符合格式要求
- **格式规则**: 10-16位数字
- **正则表达式**: `/^\d{10,16}$/`
- **示例**: `12345678901234`

**规则 DV-002**: 会员卡密码复杂度要求
- **长度要求**: 6-20位字符
- **字符类型**: 字母、数字、特殊字符组合
- **安全性**: 存储时必须加密

#### 5.2 用户数据验证
**规则 DV-003**: 手机号格式验证
- **格式规则**: 11位数字，以1开头
- **正则表达式**: `/^1[3-9]\d{9}$/`
- **示例**: `13800138000`

**规则 DV-004**: 邮箱格式验证
- **格式规则**: 符合RFC标准邮箱格式
- **正则表达式**: `/^[^\s@]+@[^\s@]+\.[^\s@]+$/`
- **长度限制**: 最大254个字符

#### 5.3 金额数据验证
**规则 DV-005**: 金额必须为非负数
- **范围规则**: ≥ 0
- **精度要求**: 保留两位小数
- **特殊值**: 0表示免费，正数表示收费

**规则 DV-006**: 金额上限限制
- **单笔交易上限**: 1,000,000元
- **单日累计上限**: 10,000,000元
- **超出处理**: 必须人工审核

### 6. 业务数据关联规则

#### 6.1 数据完整性规则
**规则 DR-001**: 外键关联必须有效
- **规则描述**: 所有外键引用必须指向存在的记录
- **引用完整性**: 级联删除或设置为空
- **异常处理**: 引用不存在时抛出数据完整性异常

**规则 DR-002**: 业务数据状态一致性
- **规则描述**: 关联数据的状态必须逻辑一致
- **示例**: 已激活的会员卡必须有关联的激活订单
- **验证时机**: 数据创建、更新、删除时

- **规则描述**: 合作伙伴角色的数据访问必须限制在自身关联范围内

- **查询优化**: 自动添加数据范围条件

**规则 PR-003**: 敏感操作需要二次确认
- **规则描述**: 删除、批量操作等敏感操作需要用户确认

- 操作记录: 记录完整的操作日志

## ⚡ 业务流程规则

### 8. 订单处理规则

#### 8.1 订单状态流转规则
**规则 BP-001**: 订单状态必须按业务逻辑流转
```typescript
// 订单状态流转规则
const ORDER_STATUS_FLOW = {
  PENDING: ['PROCESSING', 'CANCELLED'],
  PROCESSING: ['COMPLETED', 'FAILED'],
  COMPLETED: ['REFUNDED'],  // 特殊情况
  FAILED: ['PENDING'],      // 可重试
  CANCELLED: [],            // 终态
  REFUNDED: []              // 终态
};

// 状态流转条件
const ORDER_TRANSITION_CONDITIONS = {
  'PENDING→PROCESSING': '订单信息验证通过',
  'PROCESSING→COMPLETED': '交易成功且服务已激活',
  'PROCESSING→FAILED': '交易失败或服务激活失败',
  'PENDING→CANCELLED': '用户取消或超时取消',
  'COMPLETED→REFUNDED': '管理员审批通过的退款申请'
};
```

#### 8.2 订单超时规则
**规则 BP-002**: 待处理订单自动超时取消
- **超时时间**: 30分钟
- **超时处理**: 自动取消并释放资源
- **通知机制**: 向用户发送超时通知

### 9. 分账处理规则

#### 9.1 分账时间规则
**规则 BP-003**: 分账计算必须实时完成
- **计算时机**: 订单完成时立即计算
- **时间要求**: 计算时间 ≤ 5秒
- **异步处理**: 大数据量时可异步处理

#### 9.2 分账异常处理规则
**规则 BP-004**: 分账异常必须记录并告警
- **异常类型**: 数据异常、计算异常、系统异常
- **处理流程**: 记录异常 → 发送告警 → 人工介入
- **重试机制**: 可配置的重试次数和间隔

### 10. 分账规则管理规则

#### 10.1 分账规则适用性规则
**规则 BR-021**: 分账规则适用性
- **规则描述**: 分账规则仅适用于订阅订单（SUBSCRIPTION），激活订单（ACTIVATION）不参与分账计算
- **适用条件**: 规则生效时间必须有效且不重叠（同一优先级）
- **优先级规则**: 规则优先级数字越小优先级越高
- **验证逻辑**: 
  ```typescript
  function isRuleApplicable(orderType: OrderType, rule: RevenueSharingRule): boolean {
    return orderType === 'SUBSCRIPTION' && 
           rule.isActive && 
           isWithinEffectivePeriod(rule);
  }
  ```

#### 10.2 分账计算规则
**规则 BR-022**: 分账计算规则
- **规则描述**: 分账金额计算精度保留2位小数，计算过程必须可追溯和验证
- **比例范围**: 分账比例必须在合理范围内（0-100%）
- **阶梯规则**: 阶梯式规则必须连续且不重叠
- **验证逻辑**: 
  ```typescript
  function validateCommissionCalculation(amount: number, rate: number): boolean {
    const commission = amount * (rate / 100);
    return rate >= 0 && rate <= 100 && 
           commission >= 0 && 
           Number.isFinite(commission);
  }
  ```

#### 10.3 规则冲突解决规则
**规则 BR-023**: 规则冲突解决
- **规则描述**: 高优先级规则覆盖低优先级规则，相同优先级规则按创建时间先后应用
- **冲突检测**: 条件式规则的条件必须互斥或明确优先级
- **冲突处理**: 规则冲突必须记录和告警
- **验证逻辑**: 
  ```typescript
  function resolveRuleConflict(rules: RevenueSharingRule[]): RevenueSharingRule {
    return rules.sort((a, b) => {
      if (a.priority !== b.priority) return a.priority - b.priority;
      return new Date(a.createdAt).getTime() - new Date(b.createdAt).getTime();
    })[0];
  }
  ```

#### 10.4 分账异常处理规则
**规则 BR-024**: 分账异常处理
- **规则描述**: 分账计算失败必须记录详细错误信息，支持手动重算和自动重试机制
- **异常分类**: 数据异常、计算异常、系统异常
- **处理流程**: 异常记录需要人工审核和处理，分账异常必须及时通知相关人员
- **验证逻辑**: 
  ```typescript
  function handleRevenueSharingError(error: Error, record: RevenueSharingRecord): void {
    record.status = 'ERROR';
    record.errorMessage = error.message;
    record.updatedAt = new Date().toISOString();
    
    // 发送异常通知
    sendErrorNotification(error, record);
  }
  ```

#### 10.5 数据一致性规则
**规则 BR-025**: 数据一致性规则
- **规则描述**: 分账记录必须与订单数据一致，规则变更不影响已确认的分账记录
- **版本控制**: 分账重算必须生成新的版本记录
- **审计要求**: 审计日志必须完整记录所有变更
- **验证逻辑**: 
  ```typescript
  function ensureDataConsistency(order: Order, record: RevenueSharingRecord): boolean {
    return order.id === record.orderId && 
           order.amount === record.orderAmount && 
           order.status === 'COMPLETED';
  }
  ```

## 🔄 权益回收池规则

### 15. 权益回收规则

#### 15.1 回收限制规则
**规则 RP-001**: 每个MAC地址最多支持3次回收
- **规则描述**: 同一MAC地址关联的会员卡最多只能回收3次
- **限制目的**: 防止恶意回收和资源滥用
- **验证逻辑**: 
  ```typescript
  function canRecoverCard(macAddress: string, currentRecoveryCount: number): boolean {
    return currentRecoveryCount < 3;
  }
  ```

**规则 RP-002**: 回收天数计算基于实际剩余有效天数
- **规则描述**: 回收天数等于会员卡的实际剩余有效天数
- **计算时机**: 回收审批通过时计算
- **精度要求**: 精确到天，不足一天按一天计算

#### 15.2 回收池管理规则
**规则 RP-003**: 回收池天数只能通过权益回收增加
- **规则描述**: 回收池天数只能通过合法的权益回收流程增加
- **增加方式**: 仅支持权益回收审批通过后自动入池
- **禁止操作**: 禁止手动直接增加回收池天数

**规则 RP-004**: 批量兑换是唯一的天数消耗方式
- **规则描述**: 回收池天数只能通过批量兑换会员卡消耗
- **消耗方式**: 仅支持批量兑换审批通过后自动扣除
- **禁止操作**: 禁止手动直接减少回收池天数

#### 15.3 批量兑换规则
**规则 RP-005**: 兑换申请需要管理员审批
- **规则描述**: 所有批量兑换申请必须经过管理员审批
- **审批流程**: 申请 → 审批 → 执行 → 确认
- **审批权限**: 仅管理员角色有审批权限

**规则 RP-006**: 兑换天数必须小于等于回收池可用天数
- **规则描述**: 兑换申请的天数不能超过回收池当前可用天数
- **验证时机**: 申请提交时和审批执行时双重验证
- **异常处理**: 余额不足时拒绝申请并提示

#### 15.4 回收池状态规则
**规则 RP-007**: 回收池状态变更需要权限控制
- **状态流转**: ACTIVE ↔ SUSPENDED ↔ CLOSED
- **权限要求**: 状态变更需要超级管理员权限
- **审计要求**: 所有状态变更必须记录审计日志

**规则 RP-008**: 操作记录必须完整可追溯
- **记录类型**: 回收、兑换、调整三种操作类型
- **记录内容**: 操作人、时间、天数、描述等完整信息
- **查询权限**: 支持按时间、类型、操作人等多维度查询

### 16. 回收池异常处理规则

#### 16.1 回收异常处理
**规则 RP-009**: 回收审批失败必须记录详细原因
- **失败原因**: 回收限制违规、数据异常、系统错误等
- **记录要求**: 详细记录失败原因和上下文信息
- **处理流程**: 记录异常 → 通知相关人员 → 人工介入

**规则 RP-010**: 回收池余额不足时禁止兑换
- **验证时机**: 兑换申请提交时和审批执行时
- **提示信息**: 明确提示余额不足和需要补充的天数
- **处理建议**: 建议减少兑换数量或等待回收入池

#### 16.2 数据一致性规则
**规则 RP-011**: 回收池数据必须与会员卡数据一致
- **一致性要求**: 回收池总天数 = 所有回收记录天数之和
- **验证机制**: 定期数据一致性检查和修复
- **异常处理**: 发现不一致时暂停相关操作并告警

**规则 RP-012**: 回收池操作必须保证事务一致性
- **事务要求**: 回收入池和兑换扣除必须原子操作
- **回滚机制**: 操作失败时必须回滚所有相关变更
- **重试机制**: 支持有限次数的自动重试

## 🔔 通知规则

### 10. 业务通知规则

#### 10.1 通知触发条件
**规则 NR-001**: 关键业务状态变更必须通知
- **会员卡激活**: 向用户发送激活成功通知
- **订单完成**: 向合作伙伴发送分账通知
- **对账完成**: 向相关人员发送对账单通知
- **系统异常**: 向管理员发送异常告警
- **权益回收完成**: 向合作伙伴发送回收成功通知
- **批量兑换审批**: 向申请人发送审批结果通知
- **回收池余额不足**: 向管理员发送告警通知

#### 10.2 通知渠道规则
**规则 NR-002**: 根据通知类型选择合适渠道
- **紧急通知**: 短信 + 应用内通知
- **业务通知**: 应用内通知 + 邮件
- **日常提醒**: 应用内通知
- **报表通知**: 邮件 + 应用内通知

- **计算公式**: 按时完成对账周期数 / 总周期数
- **监控频率**: 每日统计
- **改进目标**: 持续优化对账流程

- **计算公式**: 正确回收池操作数 / 总操作数
- **监控频率**: 实时监控
- **告警阈值**: < 99.9% 触发告警

**规则 KPI-005**: 批量兑换成功率必须 ≥ 99.5%
- **计算公式**: 成功兑换次数 / 总兑换申请数
- **监控频率**: 每日统计
- **改进目标**: 持续优化兑换流程

**规则 KPI-003**: API响应时间必须 ≤ 2秒
- **监控指标**: 95%分位响应时间
- **监控频率**: 实时监控
- **优化目标**: ≤ 1秒

- **监控指标**: 平均审批处理时间
- **监控频率**: 实时监控
- **优化目标**: ≤ 15秒
